# M2 实施与验收记录

更新：2026-11-06。状态：实施中，尚未完成验收。用户在 M1 受控验收完成后确认按路线推进 M2；需求以 PRD P10–P12 为准。

## 实施计划

1. 多项目：从 M1 单例迁移至稳定项目 ID，保留原项目、运行、事件与工件。界面显式选择项目，创建运行固定项目与起始提交；列表和详情请求核对项目归属，切换时清理过期异步结果。
2. 有限协作：一个顶层 Run 内固定执行者与审查者两个 assignment，顺序执行，不并行写同一工作区，不递归委派、不自动反复修复。仍可显式选择原单执行流程；旧运行保持可读与可恢复。
3. 交接：执行完成后冻结包含原始代码、修改后代码及差异的只读审查上下文，记录基线、快照和完整性摘要。审查者的容器挂载强制只读，不能修改执行成果或验收命令。
4. 预算与恢复：两个角色共享运行总账和首次启动时间，每个动作附角色标识并保留分项用量。角色切换、暂停和恢复均不重置额度；每角色独立会话，未知动作必须核查，不能重放执行者已完成工作。
5. 最终验证：审查结论绑定代码快照并保存结构化问题；审查通过仍须执行固定快照验收。检查失败为失败，检查通过但审查要求修改为待检查。之后代码或交接证据变化使验证失效。
6. 整合与交付：UI 同时展示项目、角色状态、总预算、分项用量、审查结论及检查结果。采纳预检检测目标提交、分支及脏工作区，不自动覆盖。完整测试、真实容器、浏览器与受控模型验证后更新结果、提交并同步 GitHub。

## 范围边界

- 采用现有 SDK、FastAPI、PostgreSQL 与 Docker，不增加调度服务或框架。
- 一个有效 worker 顺序处理运行；两个角色是固定的有界委派，不提供任意角色图或并发执行器。
- 恢复与两个角色共享同一 Run 预算；用户明确创建的新 Run 是新授权，不宣称任意独立任务跨 Run 共享额度。
- M3–M5 不在本轮范围。真实模型继续遵守既有 campaign 累计 10 次调用、100,000 token 上限，保留 M1 的失败和未知预留。
