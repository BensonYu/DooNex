# M4 第一个纵向切片：限期后台调优批次

更新：2026-11-06。状态：**首片实现已整合，离线回归与受控真实验收进行中；尚未验收完成**。M3 现已完成 [受控验收](M3_IMPLEMENTATION.md)，本计划沿用 [路线图](ROADMAP.md) 的阶段前置条件；其样例局限和历史失败保留。采纳本设计方向不等于授权任意模型调用、候选生成或自动推广。

## 1. 首片范围与可验收流程

用户明确批准一份有到期时间的后台授权，固定一个 `tuning` 任务集、2–3 个已审核批准的 Skill 版本、一个模型配置、重复次数、每 Run/批次/每日预算和运行窗口。现有 worker 只在窗口内且没有更高优先级任务时，自动创建并执行**最多一个**固定 Arena 批次；结果可查看、可停止，可追溯至该授权。

首片流程为：创建关闭状态的授权草稿 → 查看冻结条件与用量上限 → 明确启用 → 到窗口且可派发时预留日额度并创建一个批次 → 遇用户任务安全让出 → 条件仍有效时继续 → 完成或到期停止 → 查看全部用量、失败和证据。

首片不做每日重复建批、GitHub 发现、模型生成候选、自动补跑、自动更换任务集或调参。最多一个批次的约束随重启和配置更新保持；失败、中断及未知结果不能触发再次建批。M5 的公开投稿、市场、结算和商业机制不在本计划中。

## 2. 可复用路径与真实缺口

| 现有实现 | 复用方式 / 必须补齐的部分 |
| --- | --- |
| PostgreSQL、独立 worker、全局执行锁及 owner 校验 | 保持单有效 worker，不增加服务、队列框架或并发执行器 |
| `Arena.create` 的固定计划及同事务子 Run 创建 | 沿用基线、候选、工作区和会话；需支持与后台日额度预留、授权消费在同一事务提交 |
| Run/角色/批次账本及动作意图 | 沿用预留、结算和未知记录；新增产品后台日账本，不能把受控真实验收 campaign 当作产品日预算 |
| 任务集、Skill 回执及环境完整性 | 沿用冻结和使用前复核；后台只能选择 `tuning` 与已批准版本 |
| SDK、受限 shell、固定快照验证及分类指标 | 沿用隔离与证据；必须新增可证明安全的调度让出点 |
| 普通 Run 排在 Arena Run 前 | 目前只在 Run 之间排序；不能据此承诺执行中的后台 Run 会及时让出 |

已实现后台授权、共享日账、运行窗口、事务派发及安全让出；以下是验收基线，最终结果以本页实际记录为准。

## 3. 授权与预算

后台授权默认关闭，至少记录：授权 ID 与版本、创建/启用/撤销时间、到期时间、固定任务集与候选 ID、冻结模型及环境、重复次数、窗口、每 Run 预算、批次预算、日额度和最多批次数。界面必须明确说明会消耗模型用量；凭据只保存服务端引用。

首片以 UTC 日期和 UTC 窗口为调度基准，界面同时显示明确的本地时间换算。只接受同一 UTC 日期内的有限窗口，禁止跨午夜窗口，减少首片的时区和跨日歧义；以后若支持 IANA 时区或循环窗口，另行定义夏令时与重复小时规则。

所有产品后台授权共用该日账本，不因换模型、改授权或重启获得额外日额度。每日限制至少覆盖调用数、token、累计时长及适用货币费用；每 Run 和批次继续受现有独立上限约束。`subscription` 的货币字段为 `null`，不能显示免费，也不能取消其他额度。

创建批次前，在同一数据库事务内锁定授权与日账本，检查启用、期限、窗口、当日余量、完整性及候选批准状态，先预留整批上限，再保存批次、子 Run 和授权的唯一消费关联。事务失败不能留下可执行却未计账的子 Run；已创建批次不能因重启重复预留或重复创建。

批次进入明确终态后才按可核验用量结算；调用和 token 使用实际 `calls` 与 `tokens + reserved_tokens`，时长采用明确且保守的累计口径。异常、中断或未知结果保留整批分配，直至有授权的核查结算。原始失败、未知动作和授权历史永久保留，不通过日切、删除或换 ID 退还额度。

首片不自动跨日继续旧批次。UTC 日期变化或到期后，停止其新动作并终结未启动部分；在旧日期已授权的在途请求仍归原日记录，迟到结果继续结算原记录，不转移到新日来制造空余额。日额度约束本产品按派发日接纳的用量，不承诺等同供应商账单日期或绝对费用封顶。

## 4. 用户优先与事务顺序

优先级建议固定为：普通用户 Run → 用户手动 Arena → 后台批次。后台领取、模型请求预留、工具意图以及最终检查的后续派发，都必须重新检查授权、窗口、日额度和更高优先级队列；不能只在领取 Run 时检查一次。

前台入队事务与后台派发事务必须使用同一个短期事务 advisory lock。前台先提交排队记录时，后续后台派发必须看见并让出；后台先提交动作意图时，该动作才属于允许完成的在途动作。不能用两次独立查询之间的时间差声称满足优先级。

实现前须统一锁顺序，例如「派发事务锁 → Run → 批次 → 日账本 → action」，并检查所有创建、预留、工具派发、结算和停止路径是否会反向持锁。事务只保护检查与持久化意图，不能在持锁时等待模型、容器、磁盘长操作或 worker 清理。全局 worker 会话锁继续负责单执行者，不替代这项入队/派发原子性。

用户任务不等于立即抢断已经发出的远程请求。承诺边界是：观察到更高优先级任务后不再派发新后台动作，允许当前动作在明确超时内完成并持久化，再释放 worker。首片必须限制后台模型请求、shell、验证命令和清理的最长时长，测量「前台提交 → 前台开始」延迟；发布前给出基于实际配置的上界，不预写一个未经实测的毫秒级承诺。

如果无法证明容器已停止或执行权仍有效，不能为了满足延迟数字而并行推进前台；必须显示故障阻塞并停止新后台动作。此类结果不算通过正常调度延迟验收，须保留证据和限制。

## 5. 安全调度让出与恢复

**调度让出不能复用故障 `Halt`。** 当前故障/预算停止路径会改变失败分类、标记未决动作或触发批次停止；后台因用户任务或窗口暂时不可运行而让出，需要独立的调度原因和可恢复状态，不伪造失败、不返还额度。

安全让出至少要求：已派发动作结果已持久化；Run、角色、批次和日账本一致；工作区执行摘要及 SDK 状态保存完成；恢复时任何尚未派发动作都会重新经过权限、预算和队列检查。该点必须经 SDK 合同验证，不能仅靠抛出异常推测 SDK 已安全暂停。

授权仍有效、窗口仍开放且高优先级队列为空时，只可自动继续这种有证据的调度让出。用户暂停、故障中断、未知模型用量、未知 shell 动作、残留容器、检查点漂移或无法证明 SDK 位置安全时，继续走原有核查流程，不能自动确认、重放或改为普通排队。

每次让出和继续保存原因、时间、动作/检查点引用及摘要。Run 和批次的原预算、首次启动时间、暂停耗时与未知预留保持不变；让出不延长原批次寿命。超过原 Run/批次时长、窗口截止、授权撤销或到期时停止后续派发；是否能自动继续与是否还剩预算是两个独立检查。

## 6. 数据隔离和推广边界

- 只允许冻结的 `tuning` 任务集；导入、授权、建批和使用前均校验绑定。后台不能读取 `heldout` 任务集或真实保留评测材料，不把它们作为候选调优输入。
- 只执行当前已批准且完整性有效的候选快照；计划排队期间审核、内容或控制器条件变化时拒绝新派发。Skill 声明不增加工具、宿主访问、网络或依赖安装权限。
- 沿用执行期不挂载隐藏检查器、验证期只读挂载和固定快照证据。结果供已鉴权用户查看，不进入候选生成、外部消息或其他项目。
- 后台批次仅产生调优结果。`tuning` 本已不具推广资格，仍应对后台来源增加显式拒绝推广的检查；无论分数多高，不能写入 `arena_current` 或自动替新 Run 选择 Skill。
- 真实源码、候选、检查器和会话只进入授权私有存储。产品 Git 只提交实现及可分发的合成测试，不复制真实材料。

## 8. 验证与退出条件

| 保证 | 必须实际执行的验证 |
| --- | --- |
| 显式且有限授权 | 默认关闭、未启用、过期、撤销、窗口外、错误 split、未批准候选均零派发；重启/重复请求最多创建一批 |
| 日/批次/Run 预算不绕过 | 真实 PostgreSQL 并发与事务故障注入；额度边界前置拒绝，父子与日账本可复算；失败/未知/重启/日切不返还额度 |
| 前台优先 | 用屏障控制两个事务提交顺序，证明前台先入队则后台无新派发；模拟前台在模型、工具、验证阶段到达，安全让出后先执行前台 |
| 在途延迟有界 | 慢模型传输、真实长命令及清理失败测试；记录前台提交与开始时间，验证所有等待均有明确超时和可见原因 |
| 安全继续而非重放 | SDK 模拟响应与真实容器覆盖完成动作、未执行工具、进程退出和断连；已完成动作次数不增加，未知路径不得自动继续 |
| 时钟与窗口真实生效 | 注入可控 UTC 时钟测试窗口两端、日期变化及重启；原首次启动时间不变，停机/暂停耗尽原预算后拒绝继续 |
| 资料与权限边界 | 合成 sentinel 检查模型请求、工具挂载和普通输出；验证后台拒绝 heldout，不能读管理目录、秘密或写检查器 |
| 不自动推广 | 任意成功率、结束/重启/继续/重复请求后，`arena_current` 和已有推荐历史无后台自动写入；人工入口也拒绝后台调优结果 |

先完成离线合同、数据库、真实 Docker、静态检查、前端构建与界面验收。模拟供应商响应只证明调度合同，不证明真实模型可用。

在 M3 已确认通过且用户授权明确覆盖实际模型、凭据和本次有限测试预算后，再跑一个短窗口、有限调用的受控真实后台批次，插入用户任务验证让出，分别验证停止及预算保留。记录最终代码版本、授权、配置、时间线、退出码、脱敏日志与私有工件引用，核对源工作区和推荐未被自动改动。未执行、失败、超时或不明确的项目继续标为未验证；首片全部退出条件满足后，再决定下一项 M4 能力。

## SDK 暂停合同的前置实测

2026-11-06 对锁定的 SDK 1.60.1 完成 11 项模拟传输实验（退出码 0，5.50 秒），包括两个独立 Python 进程续接同一 conversation，没有真实模型或 Docker 调用。原生 `pause()` 会完成当前模型响应的整个工具批次；当前 `should_stop` 会把尚未派发的工具消费为错误，均不能直接满足这里要求的逐动作安全让出。

私有逐工具原型通过了保存已完成 observation、只恢复剩余工具的实验；原生 SDK 在副作用发生但 observation 尚未保存时会重放动作，因此必须保留现有未知动作拒绝保护。生产方案还需绑定 session、事件头、动作身份、已结算用量、已知未派发集合和工作区摘要的数据库回执，不能靠命令字符串或 paused 字段推断安全。原始报告、失败日志和哈希保存在本机私有 `verification/m4-sdk-yield/`。此研究没有实现产品后台调度，没有验证数据库原子性、容器、并发或真实时延，M4 状态仍为待实施。
