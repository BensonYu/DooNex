# DooNex 产品需求文档

版本：0.3 · 更新：2026-11-06 · 状态：M1、M2 受控验收已完成；适用环境、样例与限制见实施记录。

## 1. 产品定位

**DooNex 是面向个人开发者的多 Agent 编程工作台，通过可恢复的执行流程、可核验的交付结果和私有 Skill 竞技，减少从需求到完成之间的手工衔接。**

项目首先部署在个人 Mac mini，通过 Web 使用。用户连接自己的模型 API，在自己授权的项目和预算范围内执行工作。后续可以扩展团队与公共生态，但不以这些扩展作为个人版本的前置条件。

本次已明确的方向：名称为 DooNex；个人使用优先；多 Agent 编程；Web 中可见的 Skill 竞技；为不同任务保留多个优秀 Skill。下面的具体技术、数量和门槛是设计与验收基线。当前实现、实测结果及未验证项见 [M2 实施记录](M2_IMPLEMENTATION.md)，历史证据见 [M1 实施记录](M1_IMPLEMENTATION.md)，不以实现存在或离线测试代替真实发布验收。

## 2. 用户问题与成功定义

| 用户问题 | 产品应提供的能力 | 如何判断有用 |
| --- | --- | --- |
| 多个项目和聊天分散，难以续接 | 项目、任务、运行历史与恢复入口 | 切换项目或刷新页面后能找到输入、变更与当前状态 |
| Agent 宣称完成，但结果不可核验 | 与代码版本绑定的交付证据 | 能区分已通过、失败、未检查和过期验证 |
| 多 Agent 互相覆盖工作或反复沟通 | 有限职责、独立工作区与明确交接 | 执行和审查的产物能合并且可追溯 |
| 不知道哪个 Skill 适合自己 | 同条件评测、基线、多维结果 | 用户能看到推荐为何适合当前任务及模型 |
| 实验和模型调用可能失控 | 共享预算、并发限制、暂停和停止 | 到达上限不再派发新调用，并显示停止原因 |

核心衡量对象是“在给定预算内通过验收的任务”，同时记录用户介入次数、成功任务成本、中断恢复结果和失败原因。首版不承诺通用成功率，也不声称一定超过其他 Agent 产品。

## 3. 用户与典型场景

首要用户是同时维护多个软件仓库的个人开发者。首批任务选取可在隔离环境中验收的缺陷修复、小功能、测试补充及有限重构。

典型流程：用户选择仓库与起始版本，写下需求和验收条件；执行 Agent 修改代码；审查 Agent 找出问题；验证器对最终修改运行检查；用户看到 diff、证据、费用和剩余限制，再决定采纳或发布。

评测场景：用户选择少量 Skill 和任务集，系统在一致环境中运行基线及候选，输出质量、稳定性、成本与耗时。用户选择适合当前场景的推荐，而非盲信单一总榜。

## 4. 范围与交付边界

| 阶段 | 必须交付 | 不属于该阶段 |
| --- | --- | --- |
| M0 | 文档与仓库规范 | 应用代码、演示数据伪装成实测 |
| M1 · 首个可用版 | 单项目单 Agent 全流程、模型接入、隔离、预算、恢复、证据 | 多 Agent 自动编排、竞技和市场 |
| M2 | 多项目管理、同一 Run 内顺序执行与只读审查、共享预算 | 并发执行器、递归委派、自动反复修复、分布式调度、任意角色组合 |
| M3 · 个人 Alpha 完整范围 | 本地 Skill 版本管理、手动触发私有竞技、多场景推荐 | 公共投稿、自动更新正在使用的 Skill |
| M4 | 预算内后台试验、候选发现和生成 | 无上限的自我迭代 |
| M5 | 公共生态与商业模式验证 | 当前版本的交付承诺 |

首版不做训练基础模型、不重新实现完整 Agent 引擎、不替代 PCB/CAD 等专业软件、不承诺兼容任意桌面应用。

## 5. 功能需求与验收

### M1：完成一个可信的任务循环

| ID | 需求 | 最小验收条件 |
| --- | --- | --- |
| P01 | 注册一个本地 Git 项目 | 校验路径和仓库；保留用户未提交改动；从明确起始提交建立独立工作区；未提交内容不静默混入任务 |
| P02 | 任务与验收条件 | 保存需求、项目、起始版本、检查命令或人工标准；开始运行后验收变更有版本记录 |
| P03 | 模型配置 | 至少接通一个实际模型 API；保存供应商、模型 ID 与能力配置；失败有可读原因；前端及日志不暴露密钥；配置档可分别供执行与审查选择，Run 冻结配置与版本；账户查询和本地用量分别展示 |
| P04 | 可见执行过程 | 展示运行状态、事件、文件变更和调用用量；浏览器刷新后继续查看同一次运行 |
| P05 | 暂停、取消与恢复 | 暂停/取消后不派发新动作；在执行动作有超时与终止状态；服务异常重启后显示中断，核对外部副作用后才能继续 |
| P06 | 工作区与工具权限 | 只访问授权项目和工具；运行环境不挂载宿主秘密或控制服务凭据；越界请求被拒绝并记录 |
| P07 | 预算控制 | 任务有调用、token、时长及适用的费用上限；启动前校验、到限停止新调用；按量计费价格未知时阻止启动；用户明确确认的包月模式费用为 null，仍限制调用/token/时长，不显示免费 |
| P08 | 完成证据 | 交付 diff、最终代码快照、实际检查命令、退出码、日志和时间；失败或未检查不能标记已验证；代码再变更使旧验证失效 |
| P09 | 采纳与发布 | 用户能查看和保留结果；整合时检测目标分支是否变化；冲突不覆盖；GitHub 推送和部署按已授权范围执行，不隐含在“本地写代码”中 |

M1 的恢复承诺是保留进度和可解释的续接，不承诺从任意系统调用中点精确恢复。单次 API 调用的在途费用可能超出估算；预算界面必须说明预估与已发生用量的差别。时长预算从首次启动累计，包含暂停时间，恢复不重置。

包月模式须有用户明确授权，费用及费用上限记录为 `null`，只按调用数、token 与时长约束调度；这不代表供应商调用免费，也不推断聊天套餐具有 API 权限。按量模式必须有单价来源及费用上限，未知价格阻止启动。两种模式均保留失败尝试、未知用量及在途预留。

当前 M1 的 P09 交付形式是安全预检、下载补丁/快照后人工采纳；不自动推送或部署。独立代码副本从 Git 对象导出，原工作区未提交内容不混入任务；技术限制见 [架构](ARCHITECTURE.md) 与 [实施记录](M1_IMPLEMENTATION.md)。

### M2：项目管理与有限协作

| ID | 需求 | 最小验收条件 |
| --- | --- | --- |
| P10 | 多项目切换 | 项目具有稳定 ID，迁移保留 M1 项目与旧运行归属；至少两个项目的运行、工作区、日志和工件互不串用；多项目请求缺少或使用错误项目上下文时拒绝访问，切换时不显示迟到的旧项目结果 |
| P11 | 执行/审查分工 | 每个角色有独立会话和明确输入、输出；审查容器只读挂载固定 before/after、diff 与交接元数据，不能修改执行工作区、基线或验收命令；结构化审查结果绑定实际代码摘要，变更或篡改使其失效，不能替代检查命令 |
| P12 | 有限委派与整合 | 一个 Run 内固定 executor 后接 reviewer，由一个有效 worker 顺序执行；共享调用、token、时长及适用费用总账，角色分项和未知预留可追溯；恢复不重跑已完成执行者；不递归或自动反复修复，最终对审查所绑定的快照重新验证 |

M2 提供 `execute` 与 `execute_review` 两种流程；后者是一个执行 Agent 加一个只读审查 Agent 的固定顺序，不提供任意任务图或并发执行器。审查要求修改时保留问题和检查结果，不自动返回执行者修复。用户明确创建的新 Run 是新授权；当前没有任意独立任务跨 Run 共享预算的能力，也不自动创建重试。后续并发须另有需求、隔离设计和本机测量。

### M3：私有 Skill Arena

| ID | 需求 | 最小验收条件 |
| --- | --- | --- |
| P13 | Skill 导入与版本管理 | 支持本地导入；记录来源、提交或内容哈希、许可证状态、内容和适用范围；内容变化产生新版本；导入不自动执行脚本 |
| P14 | 评测任务集 | 固定任务输入、起始代码、允许的检查器和环境；调优任务与保留评测任务分离；Agent 不能改动评分器 |
| P15 | 公平对比 | 同一任务集比较无额外 Skill 基线与 2–3 个候选；模型、工具、配置、资源上限一致；每次清洁重建工作区 |
| P16 | 多维证据 | 展示通过数/总数、回归、失败原因、重复运行波动、耗时、用量与费用；环境故障独立标记并保留记录 |
| P17 | 有界多场景推荐 | 默认只保留可靠优先、成本优先、速度优先三个推荐位置；结果不足可空缺或并列；显示任务类别、模型和样本量 |
| P18 | 推广与回滚 | 新版本先形成候选，用户明确选用后影响新任务；运行中的任务锁定版本；可回滚到先前推荐 |

竞技规则、失败分母与初步推荐门槛以 [Skill Arena 规范](SKILL_ARENA.md) 为唯一详细定义。

## 6. 界面与信息结构

| 页面 | 必须让用户看懂的内容 |
| --- | --- |
| 项目与任务 | 项目、任务目标、最近状态、等待用户的事项 |
| 任务详情 | 需求与验收、执行时间线、Agent 分工、变更与检查、用量、暂停/恢复入口 |
| Skills | 来源、版本、适用场景、权限需求、审核状态及历史结果 |
| Arena | 本轮任务与固定配置、进度、基线对比、多维结果、样本限制与选用入口 |
| 设置 | 模型连接、凭据引用、预算、工作区与授权工具 |

先提供清楚的状态和证据，不先做复杂工作流画布。产品界面默认中文，模型名、代码和命令保留原文；关键操作可键盘完成，状态不能只靠颜色区分。

## 7. 状态与非功能要求

- 将任务目标与每次运行分开保存；当前不可变任务输入保存在 Run 中，无独立 Task 实体或自动重试。用户明确授权的新尝试创建新 Run，不覆盖旧结果。
- 区分排队、运行、暂停请求、已暂停、等待输入/授权、验证、已验证完成、待人工检查、失败、取消和中断。
- 持久化运行事件和证据，浏览器断线不应终止后台任务；服务崩溃时不得虚构任务已完成。
- 同一运行只能由一个有效执行者持有；恢复与重试必须避免重复派发同一外部动作。
- 凭据由服务端管理，普通运行记录只引用凭据标识；敏感日志脱敏，工件默认私有。
- 默认本机访问；跨设备先使用受控私有连接。任何网络暴露都需要身份验证和明确配置。
- Mac mini / Apple Silicon 是首个验证目标；CPU、内存、磁盘与容器兼容性需实测，未验证前不宣传硬件支持范围。
- 不承诺“硬件闲置就有免费 token”。后台试验仍受模型供应商计费、限额和用户预算约束。

## 8. 发布验收与测量

M1 必须通过（当前结果限于受控样例，详见实施记录）：受控样例仓库完成一次真实模型修改与检查；失败检查阻止已验证完成；预算和取消停止后续动作；中断恢复不丢已记录的变更；原工作区未提交改动不受影响；故意越界访问被拒绝。

M2 必须通过：旧 M1 项目与运行迁移后内容和归属不变；两个项目连续运行、切换、查询和下载不串数据；缺失或错误项目上下文被拒绝。真实容器拒绝审查者写入、删除、重命名；交接和审查报告绑定同一代码摘要，篡改失效；角色总用量和未知预留之和等于共享总账，到限停止。审查期中断续接不重跑已完成执行者；最终验证期恢复不重跑模型角色；最终验收绑定审查过的固定快照。采纳预检拒绝提交、分支（包括同提交换分支）或工作区变化，不覆盖用户变更。

当前 M2 已取得离线整合检查与两个独立真实项目的执行/审查闭环证据：两角色均完成、审查批准且固定快照检查通过；首轮在审查阶段触及单 Run 调用上限并保留 `budget_exceeded` 记录。最终整合版本、迁移、容器和浏览器验收结果统一见 [M2 实施记录](M2_IMPLEMENTATION.md)。包月 campaign 无累计上限的用户授权不取消单 Run 调用/token/时长限制，历史失败和未知预留不得清除。

M3 必须通过：至少 5 个可验收任务的一次完整基线/候选对比；拟推广候选完成规定重复试验；每项分数可回到原始记录；锁定版本和回滚有效。样例通过仅证明产品流程可用，不证明某 Skill 普遍优胜。

需要持续记录的产品指标：带证据的验收通过率、成功任务模型成本、中断后成功续接数/中断总数、用户介入次数、Skill 相对基线的变化。没有足够样本时展示原始数量，不设虚构目标数值。

## 9. 长期方向与未定决策

| 事项 | 当前处理 | 决策触发点 |
| --- | --- | --- |
| SDK 复用或自研 | M1 已复用锁定版本 SDK，DooNex 自建产品层 | 后续验证发现无法满足隔离、持久化或预算要求时，以具体证据重新评估 |
| 开源范围与许可证 | 尚未选择，不添加自有项目许可证或宣称已开源 | 首次计划开放代码复用或接纳外部贡献前由维护者确定 |
| 公共 Skill 发布 | 先做私有导入与评测 | 私有评测能复查、导入安全与许可来源清楚后单独设计 |
| 作者收益分成 | 尚无收益比例或结算承诺 | 有实际收入、成本核算与反作弊数据后制定规则 |
| 空闲时自动试验 | M3 手动触发；M4 才允许受预算调度 | 手动试验稳定且能随时停止后启用 |
| 硬件与专业软件 | 保留工具接入可能，不进入个人 Alpha | 存在明确业务场景、API 和独立验收方案后立项 |

未来收入可以来自托管执行、团队功能、企业支持及市场服务。下载量不直接等于价值：分成方案需另行明确有效使用、归因、质量、反作弊、退款和可分配利润的口径，避免提前承诺“下载即获利”。
