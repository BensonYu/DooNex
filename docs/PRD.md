# DooNex 产品需求文档

版本：0.5 · 更新：2026-11-14 · 状态：M1–M3 受控验收已完成；M4 发现、生成及 UTC 2026-11-14 完整后台闭环通过，正常完整前台等待上界仍未通过，UTC 2026-11-07 两轮超时及未知预留保留；M5 自托管社区本机受控验收已通过。新增权限档位与动作审批需求 P27–P32 为待实施设计，不代表已有能力。收费规则与对外上线单独确认。适用环境、样例与限制见实施记录。

## 1. 产品定位

**DooNex 是面向个人开发者的多 Agent 编程工作台，通过可恢复的执行流程、可核验的交付结果和私有 Skill 竞技，减少从需求到完成之间的手工衔接。**

项目首先部署在个人 Mac mini，通过 Web 使用。用户连接自己的模型 API，在自己授权的项目和预算范围内执行工作。后续可以扩展团队与公共生态，但不以这些扩展作为个人版本的前置条件。

本次已明确的方向：名称为 DooNex；个人使用优先；多 Agent 编程；Web 中可见的 Skill 竞技；为不同任务保留多个优秀 Skill。下面的具体技术、数量和门槛是设计与验收基线。当前实现、实测结果及未验证项见 [M4 实施记录](M4_IMPLEMENTATION.md) 和 [M5 实施记录](M5_IMPLEMENTATION.md)，私有竞技历史见 [M3 实施记录](M3_IMPLEMENTATION.md)，M2 历史见 [M2 实施记录](M2_IMPLEMENTATION.md)，历史证据见 [M1 实施记录](M1_IMPLEMENTATION.md)，不以实现存在或离线测试代替真实发布验收。

## 2. 用户问题与成功定义

| 用户问题 | 产品应提供的能力 | 如何判断有用 |
| --- | --- | --- |
| 多个项目和聊天分散，难以续接 | 项目、任务、运行历史与恢复入口 | 切换项目或刷新页面后能找到输入、变更与当前状态 |
| Agent 宣称完成，但结果不可核验 | 与代码版本绑定的交付证据 | 能区分已通过、失败、未检查和过期验证 |
| 多 Agent 互相覆盖工作或反复沟通 | 有限职责、独立工作区与明确交接 | 执行和审查的产物能合并且可追溯 |
| 不知道哪个 Skill 适合自己 | 同条件评测、基线、多维结果 | 用户能看到推荐为何适合当前任务及模型 |
| 实验和模型调用可能失控 | 共享预算、并发限制、暂停和停止 | 到达上限不再派发新调用，并显示停止原因 |
| 频繁确认打断工作，又不清楚 Agent 能访问什么 | 可理解的权限档位、资源范围和可撤销授权 | 范围内连续工作；有效授权不重复询问；越界无副作用，等待与拒绝有明确原因 |

核心衡量对象是“在给定预算内通过验收的任务”，同时记录用户介入次数、成功任务成本、中断恢复结果和失败原因。首版不承诺通用成功率，也不声称一定超过其他 Agent 产品。

## 3. 用户与典型场景

首要用户是同时维护多个软件仓库的个人开发者。首批任务选取可在隔离环境中验收的缺陷修复、小功能、测试补充及有限重构。

典型流程：用户选择仓库与起始版本，写下需求和验收条件；执行 Agent 修改代码；审查 Agent 找出问题；验证器对最终修改运行检查；用户看到 diff、证据、费用和剩余限制，再决定采纳或发布。

评测场景：用户选择少量 Skill 和任务集，系统在一致环境中运行基线及候选，输出质量、稳定性、成本与耗时。用户选择适合当前场景的推荐，而非盲信单一总榜。

## 4. 范围与交付边界

| 阶段 | 必须交付 | 不属于该阶段 |
| --- | --- | --- |
| M0 | 文档与仓库规范 | 应用代码、演示数据伪装成实测 |
| M1 · 首个可用版 | 单项目单 Agent 全流程、模型接入、隔离、预算、恢复、证据 | 多 Agent 自动编排、竞技和市场 |
| M2 | 多项目管理、同一 Run 内顺序执行与只读审查、共享预算 | 并发执行器、递归委派、自动反复修复、分布式调度、任意角色组合 |
| M3 · 个人 Alpha 完整范围 | 本地 Skill 版本管理、手动触发私有竞技、多场景推荐 | 公共投稿、自动更新正在使用的 Skill |
| M4 | 预算内后台试验、候选发现和生成 | 无上限的自我迭代 |
| M5 | 自托管 Skill 社区：公开目录、投稿审核、条件榜单、固定版本分发和使用归因 | 多租户 SaaS、团队空间、托管用户任务及未经单独确认的收费/上线 |
| 权限与审批扩展 · 待实施 | P27–P32：权限档位、动作审批、有限授权记忆、恢复与审计 | 宿主机完全访问、任意联网、通用桌面控制；不追溯修改 M1–M5 的历史验收条件 |

首版不做训练基础模型、不重新实现完整 Agent 引擎、不替代 PCB/CAD 等专业软件、不承诺兼容任意桌面应用。

## 5. 功能需求与验收

### M1：完成一个可信的任务循环

| ID | 需求 | 最小验收条件 |
| --- | --- | --- |
| P01 | 注册一个本地 Git 项目 | 校验路径和仓库；保留用户未提交改动；从明确起始提交建立独立工作区；未提交内容不静默混入任务 |
| P02 | 任务与验收条件 | 保存需求、项目、起始版本、检查命令或人工标准；开始运行后验收变更有版本记录 |
| P03 | 模型配置 | 至少接通一个实际模型 API；保存供应商、模型 ID 与能力配置；失败有可读原因；前端及日志不暴露密钥；配置档可分别供执行与审查选择，Run 冻结配置与版本；账户查询和本地用量分别展示 |
| P04 | 可见执行过程 | 展示运行状态、事件、文件变更和调用用量；浏览器刷新后继续查看同一次运行 |
| P05 | 暂停、取消与恢复 | 暂停/取消后不派发新动作；在执行动作有超时与终止状态；服务异常重启后显示中断，核对外部副作用后才能继续 |
| P06 | 工作区与工具权限 | 只访问授权项目和工具；运行环境不挂载宿主秘密或控制服务凭据；越界请求被拒绝并记录 |
| P07 | 预算控制 | 任务有调用、token、时长及适用的费用上限；启动前校验、到限停止新调用；按量计费价格未知时阻止启动；用户明确确认的包月模式费用为 null，仍限制调用/token/时长，不显示免费 |
| P08 | 完成证据 | 交付 diff、最终代码快照、实际检查命令、退出码、日志和时间；失败或未检查不能标记已验证；代码再变更使旧验证失效 |
| P09 | 采纳与发布 | 用户能查看和保留结果；整合时检测目标分支是否变化；冲突不覆盖；GitHub 推送和部署按已授权范围执行，不隐含在“本地写代码”中 |

M1 的恢复承诺是保留进度和可解释的续接，不承诺从任意系统调用中点精确恢复。单次 API 调用的在途费用可能超出估算；预算界面必须说明预估与已发生用量的差别。时长预算从首次启动累计，包含暂停时间，恢复不重置。

包月模式须有用户明确授权，费用及费用上限记录为 `null`，只按调用数、token 与时长约束调度；这不代表供应商调用免费，也不推断聊天套餐具有 API 权限。按量模式必须有单价来源及费用上限，未知价格阻止启动。两种模式均保留失败尝试、未知用量及在途预留。

当前 M1 的 P09 交付形式是安全预检、下载补丁/快照后人工采纳；不自动推送或部署。独立代码副本从 Git 对象导出，原工作区未提交内容不混入任务；技术限制见 [架构](ARCHITECTURE.md) 与 [实施记录](M1_IMPLEMENTATION.md)。

### M2：项目管理与有限协作

| ID | 需求 | 最小验收条件 |
| --- | --- | --- |
| P10 | 多项目切换 | 项目具有稳定 ID，迁移保留 M1 项目与旧运行归属；至少两个项目的运行、工作区、日志和工件互不串用；多项目请求缺少或使用错误项目上下文时拒绝访问，切换时不显示迟到的旧项目结果 |
| P11 | 执行/审查分工 | 每个角色有独立会话和明确输入、输出；审查容器只读挂载固定 before/after、diff 与交接元数据，不能修改执行工作区、基线或验收命令；结构化审查结果绑定实际代码摘要，变更或篡改使其失效，不能替代检查命令 |
| P12 | 有限委派与整合 | 一个 Run 内固定 executor 后接 reviewer，由一个有效 worker 顺序执行；共享调用、token、时长及适用费用总账，角色分项和未知预留可追溯；恢复不重跑已完成执行者；不递归或自动反复修复，最终对审查所绑定的快照重新验证 |

M2 提供 `execute` 与 `execute_review` 两种流程；后者是一个执行 Agent 加一个只读审查 Agent 的固定顺序，不提供任意任务图或并发执行器。审查要求修改时保留问题和检查结果，不自动返回执行者修复。用户明确创建的新 Run 是新授权；当前没有任意独立任务跨 Run 共享预算的能力，也不自动创建重试。后续并发须另有需求、隔离设计和本机测量。

### M3：私有 Skill Arena

| ID | 需求 | 最小验收条件 |
| --- | --- | --- |
| P13 | Skill 导入与版本管理 | 支持本地导入；记录来源、提交或内容哈希、许可证状态、内容和适用范围；内容变化产生新版本；导入不自动执行脚本 |
| P14 | 评测任务集 | 固定任务输入、起始代码、允许的检查器和环境；调优任务与保留评测任务分离；Agent 不能改动评分器 |
| P15 | 公平对比 | 同一任务集比较无额外 Skill 基线与 2–3 个候选；模型、工具、配置、资源上限一致；每次清洁重建工作区 |
| P16 | 多维证据 | 展示通过数/总数、回归、失败原因、重复运行波动、耗时、用量与费用；环境故障独立标记并保留记录 |

### M5：自托管 Skill 社区

2026-11-06 用户明确选择本范围，具体实施和权限边界见 [M5 计划](M5_IMPLEMENTATION.md)。实现完成与公开上线分别验收，私人 Library 批准不构成公开发布授权。

| ID | 需求 | 最小验收条件 |
| --- | --- | --- |
| P22 | 公开目录与明确发布 | 默认关闭；只显示独立审核后冻结的白名单记录；公开路由不能访问任何私有项目、模型设置、原始评测或工件 |
| P23 | 有限投稿与审核 | 独立可撤销投稿权限；只接收限定公开来源，保存版本与许可；作者自报身份有清楚标识；投稿者不能发布或越权修改其他记录 |
| P24 | 固定版本分发与下架 | 下载字节、模式、摘要及许可匹配固定发布；不执行代码；下架停止新分发，保留历史；私有导入仍需独立审核 |
| P25 | 按条件展示榜单 | 同版本/任务类别/模型/环境与预算比较，显示样本和失败；自报与核验分开；缺证、过期或不可比时空缺，不把下载量当质量 |
| P26 | 可追溯使用归因 | 分发请求、自报使用与本站核验使用分开；事件幂等、权限与聚合隐私可验证；失败/取消不删除，没有实际收费不显示收益或支付成功 |

M5 当前不要求实际收付款或作者利润分配。许可证、贡献政策、对外部署和收费方案在有具体可审查内容后由维护者决定；产品不能用模拟交易或预填榜单冒充真实结果。

### 权限与动作审批：个人编程工作流扩展（规划，未实现）

2026-11-14 用户要求为 DooNex 定制权限方案并加入 PRD。本节规定目标行为，**不表示已实现四档切换、自动风险审批或通用人工审批续接**。当前产品仍在固定无网络容器中执行，已有 Skill 审核、后台授权和社区发布入口；通用 `awaiting_approval` 仅为设计状态。开发先完成当前 M4 剩余退出条件，再按[路线图](ROADMAP.md#permission-approval-plan)分片推进，本次文档更新不启用新权限或外部动作。

#### 产品决定与四档体验

默认选择 **受控自动**：日常读代码、精确修改和隔离检查连续执行；无法归入已授权操作的动作先说明再询问。提供 **项目内自主** 满足长时间编程需求，其自主范围仍是明确的项目副本。产品不提供“访问整台电脑”的 Full access 开关。

档位回答“何时询问”，资源清单回答“最多能访问什么”，二者分别保存和展示。自主程度提高不增加目录、网络、凭据或角色权限；模型调用及费用仍受原预算约束。以下是目标规则，尚无受控执行入口的能力显示“未实现”，服务端同时拒绝，不能只有按钮或授权记录而没有执行隔离。

| 档位 | 用户看到的说明 | 自动执行 | 需要确认 |
| --- | --- | --- | --- |
| 逐项确认 `ask` | 先查看，再决定是否修改或执行 | 受限结构化读取、搜索及已授权动作的结果展示 | 每个未获有效授权的写入、删除、命令执行或扩展资源请求；支持查看完整清单后一次批准一个固定批次 |
| 受控自动 `controlled` · 默认 | 自动完成常规开发，超出范围时询问 | 项目副本内的结构化读取、精确补丁及用户已允许的隔离测试/构建操作 | 任意 shell、整目录删除/清空、额外资料读取、未授权网络请求及外部写入 |
| 项目内自主 `project_auto` | 在本次项目副本与预算内连续完成工作 | 项目副本内读写、删除、shell 和检查；操作全部留痕 | 资源范围扩展及外部写入；不把选中本档视作宿主、网络或发布授权 |
| 自定义 `custom` | 按能力设置允许、询问或禁止 | 仅自动执行明确配置为允许且仍在资源上限内的动作 | 配置为询问的动作；未匹配动作默认拒绝，不提供任意脚本式审批策略 |

“已授权”可来自创建 Run 时展示并确认的范围、一次动作批准或有效的本 Run 授权；命中时直接执行并显示来源，不要求用户再点一次。保存项目模板与批准当前动作是不同操作：修改默认模板仅影响后续新 Run，不能从一次点击或聊天措辞自动生成永久权限。

受控自动不按 `ls`、`python`、`git` 等命令前缀判断安全。须提供控制器校验参数的读取、补丁和检查入口，并按实际挂载/网络能力限制它们；测试和构建仍会执行项目代码，只能运行在对应隔离副本中。通用 shell 即使看起来只读，也按命令执行处理，不能通过管道、命令替换、脚本、解释器或子进程获得更宽范围。可选模型风险解释只能增加确认或拒绝，不能把硬性禁止改为允许；首片不引入额外风险模型调用。

#### 资源与角色边界

| 资源或动作 | 本方案的默认边界与授权方式 |
| --- | --- |
| 项目副本 | 绑定稳定项目 ID、起始提交、Run 与角色。精确补丁绑定文件和前置内容；原始工作区、基线、审查快照和验收器不因副本写权限变为可写 |
| 额外资料目录 | 默认无访问；后续受控读取入口仅在用户选定、列入可申请范围的目录中导入有限只读快照。展示哪些文件会进入模型上下文及所用模型，不把“只读”解释为不会外发；拒绝秘密、链接逃逸、特殊文件及超限资料 |
| 网络 | 任务 shell 保持无网络；模型 API、现有 GitHub 发现的固定服务端入口沿用各自授权。新增网络能力必须由有限服务端入口实施，绑定目标主机/端口、方法、路径、请求数、字节上限和允许发送的数据；重定向和解析后的目标重新校验，默认拒绝回环、私网及云元数据地址。已有明确私网模型配置不成为其他网络入口的通行证 |
| 依赖安装 | 首片沿用固定镜像，在线安装不开放。后续单列依赖准备流程，绑定来源、版本/锁文件、安装脚本及产物摘要；不得用一条“允许联网”直接运行任意安装脚本 |
| 修改原项目、推送、部署及外发消息 | 不包含在任何通用档位中。必须先有专用受控入口，展示确切 diff/提交、仓库分支、部署环境或接收方及内容，绑定专门授权；授权已覆盖完全相同的待执行操作时不重复询问。当前采纳仍为预检和人工应用，不因本方案成为自动推送/部署 |
| Skill、推荐与社区 | Skill 权限声明只是申请资料；导入、审核、选用、公开发布保持不同授权。项目内自主不能自动批准 Skill、推广后台结果或发布社区内容 |
| 角色和评测 | reviewer 始终只读；候选生成保持无 shell；检查器和 heldout 隔离不变。执行者不能批准自己的请求，子角色不能继承更宽权限；角色切换不增加预算 |
| 产品硬性禁止 | 不向任务开放宿主全部磁盘、Docker socket、SSH/模型密钥、产品数据库或其他项目秘密；不允许篡改验收器、预算、权限策略及批准记录。四档及自定义都不能覆盖这些限制 |

**允许执行 = 产品硬边界、当前项目上限、Run 冻结策略与有效授权、角色能力和实际工具能力全部满足，且原预算/执行权/恢复检查通过。** 任一项禁止、缺失或无法核实即停止该动作；模型、Skill、仓库文档、网页与日志均不能授予权限。权限配置损坏或不认识的版本须拒绝新派发，不能降级成免确认模式。

#### 授权记忆与变更

- **只允许这一次**是审批按钮的默认选项。它绑定一次完整动作，不是某个命令前缀；重复点击返回同一结果。
- **本 Run 内允许此范围**只对已实现、可精确限制的能力提供。必须展示项目、角色、目录读写范围或网络目标/方法/数据范围、次数上限与有效期；不得含任意目标、无限额度或通用外部写入。审批过期时间不得晚于 Run 剩余时长、父批次窗口或已有授权到期时间。
- **保存为项目默认模板**需单独预览与保存，模板版本只用于以后新 Run。敏感外部写入不支持“以后全部允许”。已有后台、Skill 和社区授权不能转换为通用动作授权。
- Run 创建时冻结档位、策略版本、可申请的资源上限和工具/环境指纹。上限内的动作授权追加为独立记录；提高上限或改成更宽档位须明确创建新 Run，不修改旧运行输入、账本或证据。收紧权限、撤销或紧急停止须在下一次准入前生效，并保留原版本和原因。
- 批准与派发均检查撤销、期限、owner、资源和内容绑定。撤销不能收回已发送请求或已提交写入；界面分别显示“已停止新派发”和“在途结果仍待确认”，未知结果按原恢复流程处理。

#### 一个可验收的审批流程

1. 用户在项目设置选择默认模板；创建 Run 时看到实际生效的档位、项目副本、角色、网络状态、可申请范围及预算。未经用户选择的历史 Run 保留原限制，标记为旧版固定策略，不迁移为项目内自主。
2. SDK 提出工具动作后，控制器先校验结构、资源、策略与预算。`allow` 进入原动作意图/预算准入流程；`deny` 保存原因而不执行；`ask` 在副作用发生前持久化审批请求和完整动作摘要，再保存可核验的会话检查点。
3. 请求至少绑定项目、Run、角色、策略版本、SDK 会话代数/工具动作 ID、工具及参数、工作目录、目标资源、适用代码/脚本/请求体摘要、环境与有效期。批次批准须覆盖固定、有限且可逐项查看的动作列表，不能将未展示的后续动作一并批准。
4. 安全保存后进入 `awaiting_approval`：暂停本 Run 后续模型和工具派发，预算时钟继续累计，不持有数据库事务等待用户。容器/helper 已终止且无未知副作用时释放执行槽，让其他 Run 工作；无法证明安全停止时保留原阻止机制，不能用待审批状态绕过它。
5. 用户可选择“允许一次”“本 Run 内允许此范围”（仅适用时）、“拒绝此动作”或“取消运行”。拒绝的原因记录并作为工具结果返回；可在剩余预算内继续寻找合法办法，相同动作在策略未变时不反复弹窗。越权等硬性拒绝仍遵循停止和原失败分类，不能靠重试耗尽审批通知。
6. 用户批准后，worker 在短事务内复核绑定、策略撤销与预算，再消费授权、保存动作意图并领取执行权。修改过的脚本、目标、参数、环境或审批前置内容不能使用旧的一次批准；必要时重新呈现新请求。先前的用户暂停、取消和安全阻止不能被审批按钮解除。
7. 刷新、双窗口操作或进程重启不重复执行。已消费授权不能再次派发；外部动作提交确认丢失则保留未知并核查实际结果，不能把审批的幂等性宣称为外部副作用“恰好一次”。到期且尚未执行的请求不产生动作，Run 继续遵守原时长停止语义。

审批记录只保留必要的脱敏参数和内容摘要；凭据保持服务端引用，不进入提示、审批正文、事件普通字段或下载工件。批准只表示允许执行，不代表代码正确、审查通过或最终验收通过。

#### Arena 与后台的特殊规则

普通项目的默认档位不静默传入已冻结的 Arena 或后台授权。批次预先固定同一权限策略、资源、工具和非交互执行方式；基线与候选一致，策略指纹进入可比条件。首片不允许评测中临时提权或追加授权：超出冻结范围时停止并沿用既有权限失败口径，不弹窗后把有人工介入的结果算成自主通过。

后台仅执行已明确启用的有限授权；项目内自主不能启用新批次、增大日预算、读取 heldout、自动推广或恢复未知动作。普通 Run 的待审批不扩大后台能力；批次若不满足非交互授权条件，在创建/启用时拒绝并说明原因。更换权限条件需要新批次及新授权，历史证据和用量保留，不修改旧推荐的资格。

#### 新需求与验收条件

| ID | 需求 | 最小验收条件 |
| --- | --- | --- |
| P27 | 四档权限与冻结策略 | 默认受控自动；创建前可查看生效范围；未实现能力不可启用；旧 Run 不自动扩权，配置损坏拒绝派发；API 拒绝跨项目或角色策略替换 |
| P28 | 硬边界和动作决策 | 相同动作在四档下按矩阵决策；读/补丁/检查使用结构化受限入口，通用 shell 不靠字符串判安全；真实容器、路径/链接逃逸、嵌套脚本及秘密 sentinel 检查证明禁止能力未开放 |
| P29 | 可恢复的动作审批 | 从提案、等待、批准/拒绝到执行结果全链持久化；待审批期间无新模型/工具调用，安全释放 worker；重复点击、跨项目批准、过期、内容变化、暂停/取消和重启均不得重复执行或绕过检查 |
| P30 | 有限授权记忆与撤销 | 一次与本 Run 范围清晰区分；精确命中有效授权不再询问，超范围重新判断；数据库竞态验证撤销与派发顺序，模板修改不改旧 Run，未知用量和首次时钟保持 |
| P31 | 场景隔离与审计 | reviewer、生成、Arena、后台及社区各自限制不能被档位放宽；评测固定策略指纹，拒绝临时提权且不隐藏失败；每次自动放行、询问、拒绝和消费均有来源及脱敏记录 |
| P32 | 权限与审批界面 | 项目设置、创建页、任务详情和待办使用同一真实服务端状态；展示具体影响、批准范围及等待原因；刷新/双窗口一致，键盘可操作；不可用能力明确显示，批准不冒充验证完成 |

离线验证先覆盖真实 PostgreSQL 的审批消费/撤销竞态、真实 Docker 隔离和锁定 SDK 的批准/拒绝/恢复合同，再用受控模型在两个独立项目完成“精确修改请求 → 等待 → 批准一次 → 只执行一次 → 固定快照验收”的纵向流程；拒绝和重启分别保留证据。应用代码变更后重跑最终整合检查，模型验收沿用明确的凭据和有限预算。结果未知、超时和未执行项不能标为通过。

新增网络或外部写入入口各自需要独立端到端验收：目标/内容绑定、重定向及地址变化、拒绝与撤销、提交确认丢失、恢复核查和审计均通过后才开放。现有网络发现或社区发布验收不能证明新增通用能力已通过。

## 6. 界面与信息结构

| 页面 | 必须让用户看懂的内容 |
| --- | --- |
| 项目与任务 | 项目、任务目标、最近状态、等待用户的事项；权限扩展实施后增加默认档位与创建 Run 的生效范围预览 |
| 任务详情 | 需求与验收、执行时间线、Agent 分工、变更与检查、用量、暂停/恢复入口；权限扩展实施后增加当前策略、审批影响、批准来源与撤销入口 |
| Skills | 来源、版本、适用场景、权限需求、审核状态及历史结果 |
| Arena | 本轮任务与固定配置、进度、基线对比、多维结果、样本限制与选用入口 |
| 设置 | 模型连接、凭据引用、预算、工作区与授权工具；权限扩展实施后增加项目权限模板，不展示不可兑现的完全访问开关 |
| 权限待办 · 待实施 | 聚合待审批动作，显示项目/Run、具体目标及影响、有效期和停止状态；不默认勾选批量批准，不从通知自动执行 |

先提供清楚的状态和证据，不先做复杂工作流画布。产品界面默认中文，模型名、代码和命令保留原文；关键操作可键盘完成，状态不能只靠颜色区分。

## 7. 状态与非功能要求

- 将任务目标与每次运行分开保存；当前不可变任务输入保存在 Run 中，无独立 Task 实体或自动重试。用户明确授权的新尝试创建新 Run，不覆盖旧结果。
- 区分排队、运行、暂停请求、已暂停、等待输入/授权、验证、已验证完成、待人工检查、失败、取消和中断。
- 持久化运行事件和证据，浏览器断线不应终止后台任务；服务崩溃时不得虚构任务已完成。
- 同一运行只能由一个有效执行者持有；恢复与重试必须避免重复派发同一外部动作。
- 权限扩展中的待审批是一种尚未派发动作的等待；不得自动批准、停止计时或混同未知副作用恢复。模板、审批和撤销均须可追溯，具体规则以 P27–P32 为准，当前通用审批尚未实现。
- 凭据由服务端管理，普通运行记录只引用凭据标识；敏感日志脱敏，工件默认私有。
- 默认本机访问；跨设备先使用受控私有连接。任何网络暴露都需要身份验证和明确配置。
- Mac mini / Apple Silicon 是首个验证目标；CPU、内存、磁盘与容器兼容性需实测，未验证前不宣传硬件支持范围。
- 不承诺“硬件闲置就有免费 token”。后台试验仍受模型供应商计费、限额和用户预算约束。

## 8. 发布验收与测量

M1 必须通过（当前结果限于受控样例，详见实施记录）：受控样例仓库完成一次真实模型修改与检查；失败检查阻止已验证完成；预算和取消停止后续动作；中断恢复不丢已记录的变更；原工作区未提交改动不受影响；故意越界访问被拒绝。

M2 必须通过：旧 M1 项目与运行迁移后内容和归属不变；两个项目连续运行、切换、查询和下载不串数据；缺失或错误项目上下文被拒绝。真实容器拒绝审查者写入、删除、重命名；交接和审查报告绑定同一代码摘要，篡改失效；角色总用量和未知预留之和等于共享总账，到限停止。审查期中断续接不重跑已完成执行者；最终验证期恢复不重跑模型角色；最终验收绑定审查过的固定快照。采纳预检拒绝提交、分支（包括同提交换分支）或工作区变化，不覆盖用户变更。

当前 M2 已取得离线整合检查与两个独立真实项目的执行/审查闭环证据：两角色均完成、审查批准且固定快照检查通过；首轮在审查阶段触及单 Run 调用上限并保留 `budget_exceeded` 记录。最终整合版本、迁移、容器和浏览器验收结果统一见 [M2 实施记录](M2_IMPLEMENTATION.md)。包月 campaign 无累计上限的用户授权不取消单 Run 调用/token/时长限制，历史失败和未知预留不得清除。

M3 必须通过：至少 5 个可验收任务的一次完整基线/候选对比；拟推广候选完成规定重复试验；每项分数可回到原始记录；锁定版本和回滚有效。样例通过仅证明产品流程可用，不证明某 Skill 普遍优胜。

权限扩展按 P27–P32 的矩阵和分片退出条件独立验收，不把旧版的容器隔离、Skill 审核或后台启用计作通用审批通过。持续记录每 Run 的审批数、有效授权命中数、等待时长、拒绝/撤销数及阻断原因，以真实任务判断是否减少无意义打断；不预填目标百分比或把少弹窗等同更安全。

需要持续记录的产品指标：带证据的验收通过率、成功任务模型成本、中断后成功续接数/中断总数、用户介入次数、Skill 相对基线的变化。没有足够样本时展示原始数量，不设虚构目标数值。

## 9. 长期方向与未定决策

| 事项 | 当前处理 | 决策触发点 |
| --- | --- | --- |
| SDK 复用或自研 | M1 已复用锁定版本 SDK，DooNex 自建产品层 | 后续验证发现无法满足隔离、持久化或预算要求时，以具体证据重新评估 |
| 开源范围与许可证 | 尚未选择，不添加自有项目许可证或宣称已开源 | 首次计划开放代码复用或接纳外部贡献前由维护者确定 |
| 公共 Skill 发布 | M5 自托管社区本机受控验收通过，默认关闭 | 公网上线须明确公开内容、部署和贡献政策后单独确认 |
| 作者收益分成 | 尚无收益比例或结算承诺 | 有实际收入、成本核算与反作弊数据后制定规则 |
| 空闲时自动试验 | M3 手动触发；M4 才允许受预算调度 | 手动试验稳定且能随时停止后启用 |
| 硬件与专业软件 | 保留工具接入可能，不进入个人 Alpha | 存在明确业务场景、API 和独立验收方案后立项 |

未来收入可以来自托管执行、团队功能、企业支持及市场服务。下载量不直接等于价值：分成方案需另行明确有效使用、归因、质量、反作弊、退款和可分配利润的口径，避免提前承诺“下载即获利”。
