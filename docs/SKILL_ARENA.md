# Skill Arena：首版评测与推荐规范

更新：2026-11-06 · 适用：M3 私有评测 · 状态：设计基线，尚无评测结果。

## 1. 评测对象

评测的是 **Skill 的具体版本在特定任务、模型、工具、环境和预算下的表现**。不能把一次胜出解释成该 Skill 对所有任务和模型都更好，也不能将更强模型带来的提升全归因于 Skill。

Skill 的身份包含来源和内容哈希；提示、脚本或依赖有实质变化就产生新版本。缺少来源或许可记录的候选仅可按授权范围私下检查，不能自动向公共市场再分发。

角色评测暂分执行与审查两个方向。执行关注正确产物；审查关注有效问题发现、误报和验证成本。首版排行榜先比较执行角色，审查角色的独立任务集后续补齐，不把两个角色混成一张榜。

## 2. 首轮实验规模

- 选择 5–10 个可运行测试的编程任务，覆盖小缺陷、小功能和有限重构。
- 每轮比较无额外 Skill 的基线，以及 2–3 个候选版本；项目共同规范仍适用于所有组。
- 首轮可每个任务运行一次，用于排除明显失败的候选。
- 拟成为推荐的候选和对应基线，须在同一保留评测任务集上每个任务至少独立运行 3 次。
- 这些数量是可负担的起点，只能发现初步趋势与不稳定现象，不能自动构成统计显著结论。

M3 由用户手动启动一轮；后台循环、自动生成和自动发现属于 M4。

## 3. 比较时必须固定的条件

| 条件 | 记录要求 |
| --- | --- |
| 任务 | 任务集版本、任务输入、验收器版本、起始代码 commit |
| 模型 | 供应商、完整模型 ID、可用版本信息、采样/推理设置 |
| Agent | 引擎版本、角色、公共提示、上下文处理和工具集合 |
| Skill | 来源、内容哈希、依赖、传入顺序与权限需求 |
| 环境 | 镜像摘要、依赖锁、平台架构、资源及网络限制 |
| 预算 | 调用数、token、时长、费用估算上限和共享批次上限 |
| 测量 | 价格版本、缓存策略、计时口径、重试及失败分类规则 |

只有被比较的 Skill 版本应主动变化。若模型供应商不可固定快照，应记录调用时间与返回标识，并降低跨时间比较的结论强度。固定 seed 不等于确定性，供应商不支持时标为不支持。

每次从干净工作区开始，隔离会话记忆和候选之间的产物。随机化或交错安排基线与候选，减少先后顺序、机器负载和外部服务变化造成的偏差。提供商缓存不能控制时如实记录。

## 4. 验收与失败口径

任务通过须同时满足预先定义的功能验收、回归检查及权限边界；速度和价格不能抵消硬性失败。模型自述“通过”不构成证据。

| 结果 | 是否进入质量通过率分母 | 后续处理 |
| --- | --- | --- |
| 验收通过 | 是，计成功 | 保留完整证据 |
| 功能/回归失败、Agent 卡住、超时或用尽任务预算 | 是，计失败 | 不静默删除，不无限重试 |
| Skill 引起的依赖、脚本或环境失败 | 是，计失败 | 视作候选可用性问题 |
| 越权尝试、秘密暴露或篡改验收器 | 是，计失败 | 本版本禁止推广，保留审计记录 |
| 可证明与候选无关的供应商故障或宿主故障 | 否，单列环境故障 | 保留原始记录；在批次预算内对相关比较组补跑 |
| 用户中途取消 | 否，单列取消 | 批次不完整时不产生新推荐 |
| 超出预先约定的人工提示、改代码或修复 | 否，结果归入辅助运行组 | 不计自主通过率或推广所需有效次数；介入前已经发生的失败仍按原分类计入，不能通过人工介入抹去失败 |

任何失败分类都要有原因与证据，Agent 自己不能把失败改成“环境问题”。首次失败与重试全部保留，补跑不能覆盖第一次结果。

同时报告“计划尝试总数、完成数、有效尝试数、环境故障数、取消数、辅助运行数”。质量通过率使用有效尝试作为分母，不能只挑已经成功执行的任务来计算；缺少必要任务的无辅助证据时整轮不得完成推广。允许的标准澄清须在实验前定义，并一致提供给比较组。

## 5. 多维结果

| 维度 | 首版展示 |
| --- | --- |
| 正确性 | 每任务通过数/有效尝试数、全任务平均通过率、回归与权限失败 |
| 稳定性 | 每任务重复试验结果、全过/混合/全败情况及成功率区间（若实现） |
| 成本 | 各尝试模型用量、费用估算/实际状态、含失败尝试的批次总成本 |
| 单位成功成本 | 全部已发生模型成本 ÷ 验收成功次数；零成功显示不可计算 |
| 速度 | 成功尝试耗时中位数、有效尝试耗时及超时数量；排队时长单列 |
| 人工介入 | 标准澄清之外的介入次数、介入原因；辅助运行单列，不参与自主成绩和推广次数计算 |
| 可追溯性 | 代码快照、diff、检查器、命令、日志、环境与候选内容哈希 |

所有候选使用同一任务集合；任务难度不同时默认各任务等权，再在任务内聚合重复试验。不得通过给擅长的任务补跑更多次来提高总体权重。

M3 默认展示原始指标与对照变化，不默认提供加权综合分。未来若提供综合分，必须公开权重、归一化方式和适用范围，并在质量门槛之后计算。

## 6. 推荐规则

首版最多三个推荐位置，减少角色、模型和指标组合无限膨胀：

| 推荐位置 | 选择顺序 |
| --- | --- |
| 可靠优先 | 硬性门槛合格后，优先较高任务通过率，再看重复试验稳定性 |
| 成本优先 | 达到同一质量门槛后，比较含失败成本的单位成功成本 |
| 速度优先 | 达到同一质量门槛后，比较耗时，同时展示失败和超时 |

M3 的初步推广门槛：

1. 候选没有越权、秘密暴露或验收篡改；运行记录完整，必要任务都完成。
2. 所有预先标记为必过的关键任务在重复试验中全部通过。
3. 每个任务至少有一次通过；整体按任务等权的通过率不低于 80%，且不低于同轮基线。
4. 候选与基线都满足每任务至少 3 次无额外人工帮助的有效尝试；存在混合成败时显式显示“不稳定”。
5. 用户查看证据后选择是否用于新任务。此门槛只定义个人试用资格，不是普遍优胜的科学结论。

80% 为首版可调整基线；任务集定义时可以收紧，不能看到结果后为某候选降低门槛。关键任务须在运行前确定。基线也不满足要求时，可以保持推荐为空。

差异很小、样本很少或结果互有胜负时保留并列/待补证状态，不强行宣布冠军。可用非支配关系保留“质量更好但更贵”和“便宜但足够可靠”的不同候选；首版不因此自动增加推荐位置。

推荐记录包含任务类别、模型配置、角色、环境版本、样本量、生成时间及证据引用。跨模型不继承成绩，跨任务类别不直接套用总排名。

## 7. 防过拟合与不确定性

- 调优集供候选生成和改进；保留评测集的答案、隐藏测试和评分细节不返回给生成 Agent。
- 每次修改 Skill 必须形成新版本，不能把其旧版本成绩直接转移。
- 对保留任务反复挑选也会过拟合；记录试验次数，必要时更换保留任务或使用新的未见任务复核。
- LLM 评分仅用于需要语义判断的辅助维度，记录评审配置；代码正确性优先使用确定性检查。
- 一次差异可能来自模型波动、工具时序、上下文或环境。系统记录这些差异，不能承诺消除“蝴蝶效应”。
- 更新模型、引擎、环境或任务集后，旧证据仍保留，但推荐标记为待复核，不直接沿用成新的成绩。

## 8. 推广、回滚与后台实验

评测结果与当前推荐分开保存。选用新推荐仅影响之后新建的任务；正在运行的任务固定其 Skill 内容与依赖版本。推荐回滚只更改后续选择，不篡改历史成绩。

M4 才考虑自动实验：单独的每日/每轮预算，低于用户任务的优先级，限制并发与运行窗口，并支持即时停止派发。机器空闲与供应商免费额度无直接关系。

候选可由模型生成或从公开仓库发现，但星数只帮助发现；实际执行前仍需检查内容、来源、许可证、脚本和权限。自动评测不自动授予发布或替换生产 Skill 的权力。

## 9. 公共竞技的后续门槛

用户自行上传的“综合评分”只能作为自报结果展示。平台可信成绩必须来自可验证的评测记录，或由平台在受控环境中重新运行。

开放投稿与分成前，需要单独解决恶意脚本、秘密隔离、作者身份、许可证、刷下载/刷使用、归因、复现成本与申诉。下载量本身不应直接触发利润分配；具体经济规则不属于 M3。
