# DooNex 交付路线图

更新：2026-11-06 · 当前阶段：M0 文档基线。

按退出条件推进，不用未经验证的工期承诺替代验收。每个阶段完成一个可独立检查的流程，发现新约束时更新 PRD 与架构。

## M0 · 定义产品与协作方式

交付：README、PRD、架构说明、Skill Arena 规范、AGENTS.md、CLAUDE.md 和基础忽略规则。

退出条件：文档相互引用有效，范围与状态一致，无真实凭据和私人项目材料；仓库可从 GitHub 获取。**这是本次初始化范围。**

## M1 · 首个可用工作台

先做一个真实任务的纵向流程：选择 Git 项目 → 输入需求与验收 → 连接一个真实模型 → 隔离执行 → 检查固定代码快照 → 查看结果。

建议顺序：

1. 验证 OpenHands SDK 的 Apple Silicon 环境、模型接入、工具隔离、暂停/恢复及秘密持久化行为，锁定版本。
2. 建立最少的 Web 页面、API、数据库和 worker，保存项目、任务、运行与事件。
3. 加入独立工作区、权限限制、调用/时间预算和取消入口。
4. 将 diff、代码快照、检查命令与结果连接为真实交付证据。
5. 测试浏览器断线、服务中断、失败检查和用户已有未提交改动。

退出条件：满足 PRD P01–P09；新环境能按实际 README 启动；用户能看到一次真实修改及失败场景的正确状态。没有测试证据时只能交付待检查结果。

## M2 · 多项目与有限多 Agent

交付：项目切换、执行/审查分工、明确交接、统一预算与有界委派。

退出条件：满足 P10–P12；两个项目不串数据；审查绑定代码版本；并行修改不会覆盖对方；整合后的最终版本重新验证。

优先使用简单角色顺序，只有独立任务证明并行有价值时才加入并行执行。无需复杂流程画布和任意角色编排。

## M3 · 私有 Skill Arena

交付：本地 Skill 导入、不可变版本、任务集、基线对比、重复试验、多维结果、三个场景推荐与回滚。

退出条件：满足 P13–P18；用至少 5 个可验收任务比较基线及 2–3 个候选；拟推广候选及基线完成每任务至少 3 次有效试验；每个结论能追溯到实际运行记录。

此阶段完成个人 Alpha 的主要差异化能力。不能用预填漂亮分数代替真实实验，也不能因某次表现好就自动覆盖现有推荐。

## M4 · 预算内的持续改进

前置条件：M3 的手动评测流程稳定、失败分类可信、预算与停止机制有效。

探索：低优先级后台评测、GitHub 候选发现、模型生成候选、自动回归检测。先增加一个能力，再测量其成本和收益。

退出条件由该阶段单独设计：必须证明不会抢占用户任务、越过预算、泄漏保留评测信息或自动执行未审核内容。

## M5 · 公共生态与商业服务

前置条件：个人版本已经持续解决真实任务，并有可复查的评测样本与来源管理。

单独规划公开投稿、排行榜、下载/使用归因、作者激励、托管服务与团队功能。先确定项目许可证、贡献政策和数据边界，再开放外部代码贡献或市场。

任何分成都须先定义收入及成本口径、反作弊、退款和结算规则；当前没有比例和收益承诺。

## 下一项开发任务

从 **M1 的 SDK 接入验证** 开始。产物应是最小可运行流程及实际验证记录，回答：所选版本能否在目标 Mac mini 上完成隔离修改、真实检查、预算停止和中断后续接。

验证通过后，再基于实际 SDK 接口编写该阶段的实施计划和启动说明；不要先扩展完整市场或自行重写 Agent 引擎。
