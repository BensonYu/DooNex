# DooNex 交付路线图

更新：2026-11-06 · 当前阶段：M1、M2 已完成受控验收；M3 实施中，M4–M5 尚未实施。

按退出条件推进，不用未经验证的工期承诺替代验收。每个阶段完成一个可独立检查的流程，发现新约束时更新 PRD 与架构。

## M0 · 定义产品与协作方式

交付：README、PRD、架构说明、Skill Arena 规范、AGENTS.md、CLAUDE.md 和基础忽略规则。

退出条件：文档相互引用有效，范围与状态一致，无真实凭据和私人项目材料；仓库可从 GitHub 获取。**M0 文档基线已建立，后续阶段持续维护文档。**

## M1 · 首个可用工作台

先做一个真实任务的纵向流程：选择 Git 项目 → 输入需求与验收 → 连接一个真实模型 → 隔离执行 → 检查固定代码快照 → 查看结果。

M1 实施顺序与历史验收状态：

1. **兼容性与接口**：已安装并锁定 SDK 1.60.1/Python 3.12，固定 ARM64 任务镜像；已实现受控工具、持久化、预算前置与遥测边界。真实网关先前 Chat 请求失败、Responses 请求限流均保留；随后 `gpt-6.1-sol` 的 Responses 路径完成了真实样例修改和检查。
2. **产品纵向流程**：已有 React 页面、FastAPI、PostgreSQL 与独立 worker，保存运行输入、事件、动作意图、预算与证据。
3. **隔离和恢复**：已有 Git 对象独立导出、默认无网络容器、调用/token/时长及适用费用限制、暂停/取消和中断核查；旧 worker 通过全局锁与 owner 校验失效。
4. **可核验交付**：已有固定代码快照、逐命令全新检查副本、diff、退出码、日志、报告哈希绑定及变更失效。P09 仅预检与下载后人工采纳。
5. **最终验收**：M1 验收时完整测试 86 项通过，真实模型受控修改、失败检查、预算/取消、真实 worker 中断恢复和源工作区保护已有证据；真实界面工件、日志与下载最终复核通过，后续改动须重新验证。详细记录以 [M1 实施记录](M1_IMPLEMENTATION.md) 为准。

退出条件：满足 PRD P01–P09；新环境能按实际 README 启动；用户能看到一次真实修改及失败场景的正确状态。没有测试证据时只能交付待检查结果。

## M2 · 多项目与有限多 Agent

交付：稳定项目 ID 与 M1 数据迁移、项目切换、固定执行/只读审查顺序、明确交接、共享 Run 预算及可核验交付。

当前已实现：

1. **多项目**：旧项目与运行保留原归属；创建运行固定项目、路径、提交和分支；多项目查询必须指定项目上下文，界面防止迟到结果串项目。实际数据库已迁移 1 个原项目，3 个 M1 Run 完整记录前后相同。
2. **有界角色**：一个 Run 内 executor 后接 reviewer，独立会话、分项用量和共享总账；一个有效 worker 顺序处理，不递归、不自动反复修复、无并发执行器。
3. **只读交接与恢复**：新 Run 保存独立基线；审查仅看冻结的 before/after、diff 与交接元数据，Docker 挂载强制只读，数据库绑定摘要；审查/验证恢复不重跑已完成模型角色。
4. **最终证据与采纳**：结构化审查与检查结果分别保存，批准仍须实际检查；最终快照必须与审查摘要一致。采纳预检拒绝提交、同提交换分支、脏工作区和补丁冲突，不自动覆盖。
5. **验收证据**：最终应用版本完整测试 166 项、静态检查与前端构建通过，包含真实容器验证；两个独立真实项目均完成执行、只读审查批准与最终固定快照检查，原脏工作区保持不变。首轮调用到限停止的记录保留，真实界面的项目切换、审查、证据与日志已复核，详情见 [M2 实施记录](M2_IMPLEMENTATION.md)。

退出条件：满足 P10–P12；旧数据迁移和两个项目不串用；真实审查容器拒绝写入、删除、重命名；审查与最终检查绑定同一代码；角色用量、未知预留与总账一致；恢复不重放已完成角色；整合后的最终版本重新验证。受控模型闭环只证明当前环境和样例可用。

后续并行须有独立需求与测量，不作为本次 M2 退出条件；无需复杂流程画布和任意角色编排。

## M3 · 私有 Skill Arena

交付：本地 Skill 导入、不可变版本、任务集、基线对比、重复试验、多维结果、三个场景推荐与回滚。

退出条件：满足 P13–P18；用至少 5 个可验收任务比较基线及 2–3 个候选；拟推广候选及基线完成每任务至少 3 次有效试验；每个结论能追溯到实际运行记录。

此阶段完成个人 Alpha 的主要差异化能力。不能用预填漂亮分数代替真实实验，也不能因某次表现好就自动覆盖现有推荐。

## M4 · 预算内的持续改进

前置条件：M3 的手动评测流程稳定、失败分类可信、预算与停止机制有效。

探索：低优先级后台评测、GitHub 候选发现、模型生成候选、自动回归检测。先增加一个能力，再测量其成本和收益。

退出条件由该阶段单独设计：必须证明不会抢占用户任务、越过预算、泄漏保留评测信息或自动执行未审核内容。

## M5 · 公共生态与商业服务

前置条件：个人版本已经持续解决真实任务，并有可复查的评测样本与来源管理。

单独规划公开投稿、排行榜、下载/使用归因、作者激励、托管服务与团队功能。先确定项目许可证、贡献政策和数据边界，再开放外部代码贡献或市场。

任何分成都须先定义收入及成本口径、反作弊、退款和结算规则；当前没有比例和收益承诺。

用户已明确授权当前包月验收 campaign 不设累计调用/token 上限；单 Run 仍有调用、token 与时长上限，角色共享预算，费用未知为 `null`。M1 两次失败、一次成功及 M2 首轮预算停止均保留，累计账本见 [M2 实施记录](M2_IMPLEMENTATION.md)。不能通过换模型、重启或重置账本隐藏失败；受控样例不形成模型排名或通用兼容声明。
